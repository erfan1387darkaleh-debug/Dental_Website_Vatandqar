# راه‌اندازی سامانه نوبت‌دهی

این مستند، گام‌های دقیق روشن‌کردن نوبت‌دهی آنلاین (درگاه `/booking` و پنل پذیرش `/admin`) را — از پایگاه‌دادهٔ Neon تا متغیرهای محیطی و انتشار — شرح می‌دهد. هیچ اطلاعات حساب یا کلید واقعی در این پروژه وجود ندارد؛ همهٔ مقادیر را **خودتان** در گام‌های زیر می‌سازید.

## ۰. پیش‌نیازها

- Node.js ۲۰ یا جدیدتر روی سیستم/سروری که دستورها را اجرا می‌کنید.
- یک حساب در [neon.tech](https://neon.tech) (طرح رایگان برای شروع کافی است) — ساخت حساب خارج از اختیار این پروژه است.

## ۱. ساخت پایگاه‌داده در Neon

1. در داشبورد Neon یک **Project** جدید بسازید.
2. در صفحهٔ اصلی پروژه، کادر اتصال، گزینهٔ **Pooled connection** را انتخاب و رشتهٔ اتصال را کپی کنید. قالب نمونه:

```
postgresql://USER:PASSWORD@ep-XXXX-pooler.REGION.aws.neon.tech/DBNAME?sslmode=require
```

این رشته شامل گذرواژه است — آن را در چت، اسکرین‌شات یا ترمینال عمومی به اشتراک نگذارید.

## ۲. تنظیم متغیرهای محیطی محلی

```powershell
Copy-Item .env.example .env.local
```

سپس `.env.local` را باز کنید و چهار مقدار را پر کنید:

| متغیر | توضیح و دستور ساخت |
| --- | --- |
| `DATABASE_URL` | همان رشتهٔ Pooled از گام ۱ |
| `AUTH_SECRET` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `ADMIN_USERNAME` | نام ورود پذیرش (پیش‌فرض `reception`) |
| `ADMIN_PASSWORD_HASH` | `node -e "require('bcryptjs').hash('گذرواژهٔ-شما', 12).then(h => console.log(h))"` — خروجی را («$2a$12$…») در `ADMIN_PASSWORD_HASH` بگذارید، **نه** خودِ گذرواژه؛ و در `.env.local` پیش از هر `$` بک‌اسلش بگذارید (نکتهٔ زیر) |

> **نکتهٔ مهم دربارهٔ `$` در `.env.local`:** لودر متغیرهای Next مقدارهای حاوی `$` را به‌عنوان ارجاع متغیر گسترش می‌دهد و چون هش bcrypt تماماً از قطعه‌های `$…` ساخته شده (`$2a$10$…`)، مقدارِ بارگذاری‌شده به رشتهٔ خالی تبدیل می‌شود — نتیجه: ورود با خطای ۵۰۳ «تنظیم‌نشده» رد می‌شود. در فایل `.env.local` پیش از هر `$` بک‌اسلش بگذارید:
>
> ```
> ADMIN_PASSWORD_HASH=\$2a\$10\$Xk9…(بقیهٔ هش)
> ```
>
> در پنل Vercel برعکس است: مقدار را **خام و بدون بک‌اسلش** ثبت کنید (گسترش `$` آنجا انجام نمی‌شود).

متغیرهای سامانهٔ پیامک (`SMS_PROVIDER`، `KAVENEGAR_API_KEY`، `KAVENEGAR_SENDER`، `CRON_SECRET`) در بخش ۷ آمده‌اند.

فایل‌های `.env*` در `.gitignore` هستند و به مخزن یا بستهٔ کلاینت منتقل نمی‌شوند.

## ۳. ساخت جدول‌ها در پایگاه‌داده

مهاجرت آغازین از پیش ساخته شده است (`drizzle/0000_init_appointments.sql`). یک‌بار اجرا کنید:

```powershell
npx drizzle-kit migrate
```

اگر همه‌چیز درست باشد، جدول `appointments` با قیدهای زیر ساخته می‌شود:

- اندیس یکتای `(branch_id, starts_at_utc)` — تضمین دوبخشی‌بودن دو تقویم و منع نوبت هم‌زمان حتی در درخواست‌های پاراففته؛
- قیدهای CHECK روی شناسهٔ شعبه، منبع نوبت (`public`/`staff`)، قالب موبایل (`09xxxxxxxxx`)، مدت ثابت ۱۰ دقیقه و گرانولاریتی شبکه.

## ۴. اجرای محلی و آزمودن

```powershell
npm run dev
```

- `http://localhost:3000/booking` — درگاه عمومی نوبت‌دهی
- `http://localhost:3000/admin` — پنل پذیرش (تا وقتی `ADMIN_PASSWORD_HASH` خالی باشد، ورود با پیام صریح ۵۰۳ رد می‌شود)

تا وقتی `DATABASE_URL` تنظیم نشده باشد، همهٔ مسیرهای نوبت‌دهی با پیام فارسی واضح `db_unavailable` پاسخ ۵۰۳ می‌دهند؛ برنامه هرگز با دادهٔ جعلی کار نمی‌کند.

تست منطق نوبت‌دهی بدون پایگاه‌دادهٔ واقعی (روی PGlite، یک PostgreSQL واقعی به‌صورت WASM):

```powershell
npm run test:booking
```

## ۵. انتشار روی Vercel (وقتی آماده بودید)

1. مخزن را به Vercel وصل کنید (این گام به تصمیم و حساب خودتان است؛ ساخت فعلی این پروژه صرفاً محلی است و هیچ اتصال انتشار خودکاری وجود ندارد).
2. در Vercel → Project → **Settings → Environment Variables** چهار متغیر گام ۲ (همهٔ آنها: `DATABASE_URL`, `AUTH_SECRET`, `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`) را مخصوص محیط تولید ثبت کنید. مقدار هش را **خام** بگذارید (بدون بک‌اسلش؛ قاعدهٔ `$` فقط برای فایل `.env.local` است).
3. مقدار `DATABASE_URL` در Vercel همان رشتهٔ Pooled Neon است؛ بنابراین یک بار (و پس از هر تغییر schema) دستور زیر را با همان متغیر محلی اجرا کنید:

```powershell
npx drizzle-kit migrate
```

## ۶. نکات و محدودیت‌های شناخته‌شده

- **کوکی‌های نشست** در محیط HTTPS علامت `Secure` می‌گیرند؛ روی لوکال HTTP برای دیدن پنل کافی است — برای تولید الزاماً HTTPS لازم است (Vercel پیش‌فرض دارد).
- **محدودسازها** (سقف ورود ناموفق، نرخ رزرو و خواندن موجودی) در حافظهٔ هر نمونهٔ سرورند؛ برای چند نمونهٔ پارافته در آینده می‌توان به محدودساز با لایهٔ مشترک اضافه کرد.
- تغییر/لغو نوبت از سوی مراجع تعریف نشده است — فقط پذیرش حذف می‌کند و مراجع با تلفن هماهنگ می‌کنند.
- برای `drizzle-kit push` یا `migrate` ارتباط اینترنت به Neon لازم است؛ هرگز رشتهٔ اتصال را در کد یا فایل‌های عمومی جاسازی نکنید.

## ۷. سامانه پیامک نوبت‌ها (تأیید ثبت و یادآوری)

دو پیامک خودکار وجود دارد:

| پیامک | چه زمانی | محتوای کلیدی |
| --- | --- | --- |
| **تأیید ثبت** | بلافاصله پس از ثبت نوبت عمومی (پس از فرستادن پاسخ به مراجع؛ تأخیر یا شکستش ثبت نوبت را تحت‌تأثیر نمی‌گذارد) | نام بیمار، تاریخ و ساعت جلالی صریح، نام و تلفن شعبه |
| **یادآوری** | فراخوانی زمان‌بندی‌شدهٔ `/api/booking/reminders` (کرون روزانه یا اجرای دستی) | تاریخ و ساعت جلالی صریح (هرگز «فردا» نمی‌گوید)، نام و تلفن شعبه |

پنجرهٔ یادآوری: هر نوبتِ «تأییدشده»ای که هنوز شروع نشده و تا پایان روزِ فردای تهران باقی است. هر نوبت حداکثر یک پیامک یادآوری می‌گیرد (ستون `reminder_sent_at`)؛ شکست ارسال برای اجرای بعدی دوباره تلاش می‌شود و دو اجرای هم‌زمان هرگز پیامک تکراری نمی‌فرستند.

### ۷.۱. متغیرهای محیطی پیامک

| متغیر | توضیح |
| --- | --- |
| `SMS_PROVIDER` | `kavenegar` برای ارسال واقعی؛ `mock` فقط برای توسعهٔ محلی. **تا وقتی تنظیم نشود، هر ارسال «شکست صریح» می‌خورد (`sms_provider_not_configured`) — هیچ رفتار جعلی پیش‌فرضی وجود ندارد.** |
| `KAVENEGAR_API_KEY` | کلید API از پنل [kavenegar.com](https://kavenegar.com) (فقط برای `kavenegar`) |
| `KAVENEGAR_SENDER` | خط ارسال (اختیاری؛ خالی = خط پیش‌فرض حساب) |
| `CRON_SECRET` | کلید فراخوانی مسیر یادآوری — `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |

⚠️ `SMS_PROVIDER=mock` پیامک را «موفق» علامت می‌زند بدون ارسال واقعی (فقط گزارش سرور) — هرگز در محیط تولید تنظیمش نکنید. کلید API و `CRON_SECRET` هرگز در گزارش‌ها یا پاسخ‌های API ظاهر نمی‌شوند.

### ۷.۲. تغییر پایگاه‌داده (یک‌بار)

مهاجرت جدید در `drizzle/0001_add_sms_fields.sql` است و این‌ها را به جدول `appointments` می‌افزاید: ستون `status` (پیش‌فرض `confirmed`، فقط `confirmed`/`cancelled`)، `reminder_sent_at`، `confirmation_sent_at` و اندیس `starts_at_utc`.

**اعمال روی پایگاه‌دادهٔ Neon (اجباری):** محتوای همین فایل را کامل، یک‌بار، در **SQL Editor** داشبورد Neon اجرا کنید (همان روش اعمال مهاجرت آغازین). اگر جدول را دستی ساخته‌اید، از اجرای `npx drizzle-kit migrate` خودداری کنید — کتابچهٔ مهاجرت در پایگاه‌داده ثبت نشده و `migrate` دوباره مهاجرت آغازین را اجرا می‌کند و خطای «table already exists» می‌دهد. اجرای مکرر این فایل هم خطا می‌دهد (idempotent نیست) — علامت درستیِ اجرا، خطای «duplicate column» است، یعنی قبلاً اعمال شده.

### ۷.۳. زمان‌بندی یادآوری

- فایل `vercel.json` یک کرون روزانه ثبت کرده است: `30 14 * * *` به UTC = **ساعت ۱۸:۰۰ تهران** — عصرِ روز قبل، نوبت‌های فردا یادآوری می‌شوند.
- در Vercel → Settings → Environment Variables، متغیر `CRON_SECRET` را ثبت کنید؛ Vercel خودش سرآیند `Authorization: Bearer` را می‌فرستد. فراخوان بی‌کلید یا کلید اشتباه پاسخ ۴۰۱ می‌دهد.
- اجرای دستی (پس از تنظیم `DATABASE_URL` و `CRON_SECRET` در `.env.local`):

```powershell
$secret = "مقدار-CRON_SECRET-شما"
Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/booking/reminders" -Headers @{ Authorization = "Bearer $secret" }
```

- پاسخ فقط شمار است و هیچ شمارهٔ تلفنی ندارد، مثل: `{"ok":true,"reminders":{"considered":3,"sent":3,"failed":0,"skipped":0,"failedAppointmentIds":[]}}`

## ۸. نظرات بیماران (تعدیل‌شده)

بخش «تجربهٔ مراجعان ما» در صفحهٔ اصلی، نظرات تأییدشدهٔ بیماران را نشان می‌دهد و فرم «ثبت نظر شما» را هم دارد. جریان کار:

1. بیمار از فرم صفحهٔ اصلی نظر می‌فرستد (`POST /api/testimonials`) — نظر همیشه با وضعیت «در انتظار تأیید» ذخیره می‌شود (ضد اسپم: ۳ نظر در ۱۰ دقیقه از هر IP).
2. پذیرش در پایین پنل `/admin` بخش «نظرات بیماران» را می‌بیند: فیلتر «در انتظار تأیید/تأییدشده/همه»، دکمهٔ «تأیید و نمایش» و «حذف» (با تأیید دومرحله‌ای).
3. فقط نظرات تأییدشده (`is_approved = true`) در `GET /api/testimonials` و صفحهٔ اصلی ظاهر می‌شوند.

نوع خدمت هر نظر از فهرست مرکزی `data/services.ts` می‌آید؛ برای افزودن خدمت جدید فقط همان فایل را ویرایش کنید (قید CHECK پایگاه‌داده همان فهرست را تضمین می‌کند — پس از تغییر فهرست، مهاجرت جدیدی لازم است).

### ۸.۱. تغییر پایگاه‌داده (یک‌بار)

مهاجرت `drizzle/0002_add_testimonials.sql` جدول `testimonials` را می‌سازد (نام، متن، امتیاز ۱–۵، نوع خدمت، وضعیت تأیید، زمان ثبت + اندیس). اجرای آن همان روش بخش ۷.۲ است: محتوای فایل را یک‌بار، به‌ترتیب **پس از** مهاجرت ۰۰۰۱، در SQL Editor داشبورد Neon اجرا کنید. خطای «relation already exists» یعنی قبلاً اعمال شده.

### ۸.۲. استفادهٔ دستی از API پذیرش (بدون رابط کاربری)


## ۹. نمونه‌کارهای قبل و بعد (پرترهٔ نتایج)

بخش «قبل و بعدِ درمان‌ها» در صفحهٔ اصلی (پیش از «تماس با ما») نمونه‌های منتشرشده را با اسلایدر مقایسه نشان می‌دهد؛ کاربر دستگیرهٔ تصویر را می‌کشد (یا کلیک/کلیدهای جهت‌دار) تا تفاوت پیش و پس از درمان را ببیند. جریان کار:

1. پذیرش در پایین پنل `/admin` بخش «نمونه‌کارهای قبل و بعد» را می‌بیند: دکمهٔ «افزودن نمونه»، ویرایش، «انتشار/پنهان‌سازی» و «حذف» (با تأیید دومرحله‌ای) + فیلتر همه/منتشرشده/پیش‌نویس.
2. نمونهٔ تازه به‌طور پیش‌فرض «منتشرشده» است؛ با برداشتن تیکِ نمایش در فرم، به‌صورت پیش‌نویس ذخیره می‌شود و از سایت عمومی پنهان می‌ماند (حذف کامل لازم نیست).
3. بازدیدکنندگان در `GET /api/gallery` فقط نمونه‌های منتشرشده را می‌بینند؛ فیلتر «نوع خدمت» همان فهرست مرکزی `data/services.ts` است (مثل نظرات؛ پس از تغییر فهرست خدمات، مهاجرت جدیدی برای قید CHECK لازم است).

### ۹.۱. تصاویر کجا باشد؟

این پروژه سرویس ذخیرهٔ فایل ندارد (آپلود مستقیم از مرورگر ممکن نیست)؛ آدرس تصویر را در فرم وارد کنید — دو شکل مجاز است:

- **مسیر نسبی سایت:** فایل را در پوشهٔ `public/before-after/` بگذارید و آدرس `/before-after/case-1-before.jpg` را وارد کنید (نیازمند استقرار مجدد برای فایل‌های تازه).
- **نشانی https:** تصویر را در هر میزبان تصویر (مثلاً Vercel Blob، Cloudinary یا حتی تلگرام/رubicای مناسب) بارگذاری کنید و نشانی کامل `https://...` را وارد کنید — بدون نیاز به استقرار مجدد. طرح‌های دیگر (http ناامن، `javascript:` و مانند آن) در سمت سرور رد می‌شوند.

برای آپلود مستقیم در آینده، افزودن Vercel Blob یک مسیر API و یک متغیر محیطی می‌خواهد؛ در صورت نیاز اضافه می‌شود.

### ۹.۲. تغییر پایگاه‌داده (یک‌بار)

مهاجرت `drizzle/0003_add_gallery.sql` جدول `gallery_cases` را می‌سازد (عنوان، توضیح اختیاری، نوع خدمت، دو آدرس تصویر، وضعیت انتشار، زمان ثبت + اندیس). اجرای آن همان روش بخش ۷.۲ است: محتوای فایل را یک‌بار، به‌ترتیب **پس از** مهاجرت‌های ۰۰۰۱ و ۰۰۰۲، در SQL Editor داشبورد Neon اجرا کنید. خطای «relation already exists» یعنی قبلاً اعمال شده.

### ۹.۳. استفادهٔ دستی از API پذیرش (بدون رابط کاربری)

```powershell
# فهرست همهٔ نمونه‌ها (نیازمند کوکی نشست پذیرش)
Invoke-RestMethod -Uri "http://localhost:3000/api/admin/gallery?status=all" -WebSession $session

# افزودن نمونه
Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/admin/gallery" -ContentType "application/json" -WebSession $session -Body (@{ title = "ایمپلنت پیشین"; description = "نمونهٔ درمان"; treatmentType = "prosthesis"; beforeImageUrl = "/before-after/b.jpg"; afterImageUrl = "/before-after/a.jpg" } | ConvertTo-Json)

# پنهان‌سازی/انتشار (فقط فیلدهای ارسالی تغییر می‌کنند)
Invoke-RestMethod -Method Patch -Uri "http://localhost:3000/api/admin/gallery?id=شناسه-نمونه" -ContentType "application/json" -WebSession $session -Body (@{ isPublished = $false } | ConvertTo-Json)

# حذف
Invoke-RestMethod -Method Delete -Uri "http://localhost:3000/api/admin/gallery?id=شناسه-نمونه" -WebSession $session
```

## ۱۰. امنیت (تدوین‌شده در بازرسی امنیتی)

لایه‌های امنیتی سایت و محل تنظیم هرکدام — برای تغییر، همین فهرست را مرجع بگیرید.

### ۱۰.۱. سرصفحه‌های امنیتی (next.config.ts)

همهٔ مسیرها (صفحات و API) این سرصفحه‌ها را می‌گیرند: `Content-Security-Policy`، `X-Frame-Options: DENY`، `X-Content-Type-Options: nosniff`، `Strict-Transport-Security` (دو سال + زیردامنه‌ها؛ بدون preload)، `Referrer-Policy: strict-origin-when-cross-origin`، `Permissions-Policy` (دوربین/میکروفون/موقعیت و… بسته) و `Cross-Origin-Opener-Policy: same-origin`.

نکتهٔ CSP: این پروژه با cacheComponents/PPR ایستا پیش‌رندر می‌کند و CSP مبتنی بر nonce با آن ناسازگار است؛ بنابراین الگوی رسمی «بدون nonce» اعمال شده (`script-src 'self' 'unsafe-inline'` — فقط برای اسکریپت‌های درونی خود Next/React؛ سایت هیچ اسکریپت یا استایل بیرونی‌ای ندارد). اگر روزی به CSP سخت‌گیرانه (بدون unsafe-inline) نیاز شد: یا قابلیت آزمایشی SRI در Next یا مهاجرت همهٔ صفحه‌ها به رندر دینامیک با nonce از طریق proxy.

### ۱۰.۲. سقف‌بانی درخواست‌ها (Rate Limiting)

همهٔ سقف‌ها در حافظهٔ نمونهٔ سروراند (lib/api/http.ts) و روی Vercel هر نمونهٔ تابع جدا شمرده می‌شود؛ برای مطب این مقیاس کافی است و دفاع در برابر DDoS حجمی وظیفهٔ لبهٔ شبکه (مثل Vercel) است:

| مسیر | سقف |
| --- | --- |
| `POST /api/booking/create` | ۸ در دقیقه از هر IP |
| `GET /api/booking/availability` | ۶۰ در دقیقه از هر IP |
| `POST /api/testimonials` | ۳ در ۱۰ دقیقه از هر IP |
| `GET /api/testimonials` | ۶۰ در دقیقه از هر IP |
| `GET /api/gallery` | ۶۰ در دقیقه از هر IP |
| `POST /api/admin/login` | ۱۰ در دقیقه + ۵ خطا در ۱۰ دقیقه |
| `GET /api/booking/reminders` (کرون) | گارد CRON_SECRET |

علاوه بر این، بدنهٔ JSON همهٔ مسیرهای نوشتنی با سقف ۱۶KB خوانده می‌شود (`readJsonBody`) تا خواندنِ بی‌کران بدنه مسیر کمبود حافظه باز نکند.

### ۱۰.۳. اعتبارسنجی و پایگاه‌داده

- همهٔ پرس‌وجوهای Drizzle پارامتری هستند؛ ورودی کاربر هیچ‌جا در SQL درج نمی‌شود (تنها `sql.raw` فهرست خدمات است که دادهٔ زمان-ساخت است، نه ورودی کاربر).
- اعتبارسنجی کامل ورودی در سمت سرور در سه لایه: سرویس‌های دامنه (lib/booking, lib/testimonials, lib/gallery — سخت‌گیرانه و تست‌شده با ۶۵ تست)، قیدهای CHECK پایگاه‌داده (امتیاز، خدمت، طول متن) و مسیر API (ساختار بدنه، مبدأ، سقف حجم).
- ورودی کاربر هرگز به HTML خام نمی‌رسد؛ دو مورد `dangerouslySetInnerHTML` موجود هر دو ثابت سمت سرورند (اسکریپت تم و JSON-LD) و توسط ابزار بازرسی مجاز شده‌اند.

### ۱۰.۴. نشست پنل پذیرش

کوکی `dental_admin_session`: `httpOnly`، `sameSite=strict`، `secure` روی https، `maxAge` هم‌اندازهٔ عمر توکن (۱۲ ساعت). توکن = payload.{HMAC-SHA256 با AUTH_SECRET} و مقایسهٔ زمان‌ثابت. گذرواژه فقط به‌صورت هش bcrypt در `ADMIN_PASSWORD_HASH` — هیچ مقدار پیش‌فرضی وجود ندارد و نبود آن ورود را می‌بندد (۵۰۳).

### ۱۰.۵. رازها و بازرسی خودکار

هیچ متغیر `NEXT_PUBLIC_*`ای در پروژه نیست؛ همهٔ فایل‌های `.env*` در `.gitignore`اند. بازرسی سریع برای CI (بدون وابستگی):

```powershell
npm run check:security
```

این اسکریپت چهار چیز را می‌سنجد: نبود `NEXT_PUBLIC_` در کد، رهگیری‌نشده بودن فایل‌های env در گیت، نبود مقدار جایگزین سخت‌کدشده برای هر راز (`?? "..."` کنار DATABASE_URL/SECRET/PASSWORD/KEY/TOKEN — هم‌جنس حفرهٔ «admin123» که در بازرسی بسته شد)، و مجازبودن محل‌های `dangerouslySetInnerHTML`.

### ۱۰.۶. خطاها و لاگ

پاسخ‌های خطای API همیشه فقط «کد + پیام فارسی»اند (`jsonError`)؛ پیام خطای واقعی، استک و جزئیات پایگاه‌داده هرگز به کلاینت نمی‌رود و فقط در گزارش سرور (`console.error` با پیشوند مسیر) ثبت می‌شود.
